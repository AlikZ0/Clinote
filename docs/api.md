# API contract (v1)

Base: `/api/v1`. JSON in, JSON out, except signed-URL uploads which go straight
to object storage (§74).

## 1. Conventions

- Auth: `Authorization: Bearer <access token>`; refresh via `HttpOnly` cookie.
- Every request may carry `X-Clinote-Device: <deviceId>`.
- Errors are typed:

```json
{ "error": { "code": "feature_not_available", "message": "…", "details": {} } }
```

Codes: `unauthenticated`, `forbidden`, `not_found`, `validation_failed`,
`feature_not_available`, `device_limit_reached`, `storage_limit_reached`,
`rate_limited`, `conflict`, `internal`.

- Pagination is cursor-based: `?cursor=&limit=`, response `{ items, nextCursor, hasMore }`.
- All request/response shapes are zod schemas exported from `packages/types`.

## 2. Auth — `/auth`

```
POST /auth/register            { email, password }            → { user, tokens }
POST /auth/login               { email, password }            → { user, tokens }
POST /auth/refresh             (cookie)                       → { tokens }
POST /auth/logout                                             → 204
POST /auth/forgot-password     { email }                      → 202 (always)
POST /auth/reset-password      { token, password }            → 204
```

## 3. Users and keys — `/users`

```
GET  /users/me                        → { user, entitlement }
PATCH /users/me                       { name?, locale?, timezone? }
GET  /users/me/keys                   → { salt, kdf, iterations, wrappedDekSync }
PUT  /users/me/keys                   { salt, kdf, iterations, wrappedDekSync, wrappedDekRecovery }
DELETE /users/me                      account deletion (async, confirmed)
```

The server stores wrapped key material only (see `encryption.md`).

## 4. Devices — `/devices`

```
GET    /devices                       → [{ id, name, platform, lastSeen, createdAt }]
POST   /devices                       { name, platform } → device  (409 device_limit_reached)
PATCH  /devices/:id                   { name }
DELETE /devices/:id                   revokes sync + push for that device
```

The device **id is generated by the device** and sent by the client: the same id
stamps every sync envelope and hybrid clock value (docs/sync.md §2), so a
server-assigned id would leave the outbox referring to a device that does not
exist. `POST /devices` is therefore an idempotent upsert — re-registering an
existing device does not consume another slot.

## 5. Sync — `/sync`

```
POST /sync/push        { envelopes: [ { operationId, entityType, entityId,
                                        operation, hlc, deviceId, payload } ] }
                       → { accepted: [operationId], seq: { operationId: seq } }
GET  /sync/changes?since=<seq>&limit=  → { items, nextCursor, hasMore }
GET  /sync/status                      → { serverSeq, deviceCursor, pending }
```

`payload` is base64 ciphertext. Push is idempotent on `operationId`.

## 6. Backups — `/backups`

```
POST /backups/init        { size, checksum, deviceId, parts }
                          → { backupId, uploadUrls, expiresAt }
POST /backups/complete    { backupId, parts, checksum } → { status }
GET  /backups             → [{ id, createdAt, size, status, deviceId, appVersion,
                               databaseVersion }]
GET  /backups/:id/download → { url, expiresAt }
DELETE /backups/:id
GET  /backups/health      → { lastSuccessfulBackup, lastFailedBackup,
                              successCount30d, failureCount30d, storageUsed }
```

## 7. Appointments — `/appointments`

The appointment _records_ live on the device and travel through `/sync`. This
namespace carries only reminder scheduling (see `notifications.md` §1):

```
PUT    /appointments/schedules   { schedules: [{ ref, fireAt, kind }] }
DELETE /appointments/schedules   { refs: [ref] }
GET    /appointments/schedules   → [{ ref, fireAt, kind, state }]
```

## 8. Notifications — `/notifications`

```
GET  /notifications/preferences        → preferences
PUT  /notifications/preferences        preferences
POST /notifications/push/subscribe     { endpoint, keys, deviceId }
DELETE /notifications/push/subscribe   { endpoint }
POST /notifications/test               sends a test to this device
```

## 9. Subscriptions — `/subscriptions`

```
GET  /plans                            → plan catalog (public, cacheable)
GET  /subscriptions/me                 → { subscription, entitlement }
POST /subscriptions/checkout           { planId, interval } → { url }
POST /subscriptions/cancel             → { subscription }
POST /subscriptions/restore            → { subscription | null }
POST /webhooks/billing/:provider       provider webhook, signature-verified
```

## 10. Workspaces — `/workspaces` (Business)

```
GET    /workspaces                        → [{ id, name, role, memberCount }]
POST   /workspaces                        { id, name, sealedKey }
PATCH  /workspaces/:id                    { name }
GET    /workspaces/:id/members            → [{ userId, email, role, joinedAt, hasKey }]
POST   /workspaces/:id/invites            { email, role }   → { invite, token? }
GET    /workspaces/:id/invites            → pending invitations
DELETE /workspaces/:id/invites/:inviteId
POST   /workspaces/invites/accept         { token }         → { workspace, awaitingKey }
PATCH  /workspaces/:id/members/:memberId  { role }
DELETE /workspaces/:id/members/:memberId
GET    /workspaces/:id/audit?limit=&before= → audit events

GET    /workspaces/:id/key                → the caller's sealed workspace key
GET    /workspaces/:id/keys/pending       → members with no key, and their public keys
PUT    /workspaces/:id/keys/:memberId     { sealedKey }

GET    /users/me/identity                 → { publicKey, wrappedPrivateKey }
PUT    /users/me/identity                 { publicKey, wrappedPrivateKey }
```

Notes that are not obvious from the shapes:

- **The workspace id comes from the device.** The workspace key is sealed _to_
  the id, and sealing happens on the device, so the device has to know the id
  before it sends the request. A server-assigned id would need a second call
  that could fail and leave a workspace nobody can open.
- **`sealedKey` is opaque.** The server stores it and hands it back; it has no
  code that could open one, and `PUT .../keys/:memberId` is refused unless the
  caller already holds the key themselves.
- **`token` is returned only outside production**, where there is no mail
  server to read the invitation from.
- **Which workspace a sync call is about travels in `X-Clinote-Workspace`**,
  not in the path — it is ambient for every call, like `X-Clinote-Device`. It
  must appear in the CORS allow-list or every browser request fails preflight.
- **Membership is checked before existence.** A non-member gets `404` for a
  workspace that exists and for one that does not.

## 11. Health

```
GET /health/live      → 200
GET /health/ready     → dependencies (db, storage, queue)
```

## 12. Rate limits

Auth routes: strict per IP + per account. `/sync/push`: per device, burst +
sustained. `/backups/init`: low, per account. Limits return `429` with
`Retry-After` and the `rate_limited` code.
